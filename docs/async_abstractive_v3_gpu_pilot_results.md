# V3 异步摘要证据图 GPU 小样本重跑

## 实验配置

- 数据集：HotpotQA、2WikiMultiHopQA、MuSiQue。每个数据集各取一个三轮相关问题序列，共 9 个问题。
- 生成模型：Qwen2.5-7B-Instruct GGUF Q4_K_M，未设置固定生成 token 上限。
- V3 摘要模型：Qwen2.5-0.5B-Instruct，CUDA，摘要最多 64 tokens。
- 对比方法：无压缩、官方 LLMLingua-2、本项目 V2 融合图、V3 异步摘要融合图。
- 轮间等待：1 秒。V3 在答复后异步摘要本轮原始证据；后续请求只融合当前原始证据与已完成的会话摘要。
- 统计：F1/EM 及 Token 减少率按 9 个请求汇总；平均完整请求延迟从压缩开始计至答案生成返回，包含同步请求路径，不包含答复后的后台摘要计算。

## V3 后台摘要诊断

- 摘要模型配置为 CUDA；后台任务无错误，但 6 个可检查的下一轮中 **0 个摘要按时完成**，完成率为 **0/6（0%）**。下一轮实际选中的压缩记忆数为 0。
- 后台任务平均计算时间约 **5.65 秒**，平均排队时间约 **2.53 秒**，平均总耗时约 **8.52 秒**。这显著超过 1 秒轮间隔，所以本次 V3 质量结果并没有测到已生成摘要记忆带来的收益。
- 发起异步摘要对当前回答路径的同步压缩计时平均约 **46 ms**；该值仅表示提交/调度的请求路径时间，**不代表摘要完成耗时**。后台摘要完成时间单独记录，不纳入完整请求延迟。
- 尽管异步摘要不会等待完成再返回当前答案，GPU 上摘要与 7B 生成并行运行会竞争计算资源。V3 的完整请求平均延迟为 **3933 ms**，高于 V2 的 **1145 ms** 和无压缩的 **1391 ms**。LLMLingua-2 平均为 3250 ms，且其耗时含请求前压缩。

## 解释与限制

这次重跑说明“把摘要放到 CUDA”本身不足以保证它赶上下一轮：此处 0.5B 摘要任务的队列与计算耗时远大于一秒空窗，且同时运行 7B 生成时会造成 GPU 资源竞争。因而，本轮 V3 与 V2 的相近 F1（0.1015 对 0.0984）不能解释为摘要记忆有效；下一轮没有读到摘要。V3 的延迟高也反映了同一 GPU 上并行计算的干扰。

每个数据集只有一个三轮序列，总计 9 个请求，且它们是从多跳问答资料中构造的相关序列，并非真实用户对话。结果适合诊断执行时序，不足以支持稳定的质量排序。若要检验记忆收益，应增加轮间空窗或优化摘要吞吐，并确保下一轮前完成率足够高；也可在独立 GPU/CPU 资源上运行摘要模型以避免与 7B 争用。
